# Task 2: Functional Requirements Specification

The system defines 14 testable Functional Requirements (FR01 through FR14), satisfying the requirement for at least 12 functional specifications.

| ID | Requirement Title | Detailed Specification | Source Stakeholder | Priority | Measurable Acceptance Criteria |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **FR01** | Authentication and Server-Side Authorization | All protected API commands shall mandate a cryptographically signed session token (JWT) and evaluate server-side role assignments for every request. Client-side role declarations shall be ignored. | Administrator, All Roles | **Must** | Requests lacking an `Authorization` header receive HTTP 401 Unauthorized; authenticated requests lacking required role receive HTTP 403 Forbidden across 100% of protected endpoints. |
| **FR02** | Order Placement and Line Validation | The system shall validate order line quantities, product existence, and customer ownership before persisting an order in the database. | Customer | **Must** | Non-positive quantities (<= 0) or unlisted SKUs return HTTP 422 Unprocessable Entity. Valid requests persist an order with state `PLACED`, a unique UUID, and the caller's user ID as `owner_id`. |
| **FR03** | Atomic Stock Reservation | The system shall reserve requested stock atomically within the same database transaction as order placement. | Customer, Warehouse Picker | **Must** | When two concurrent requests contend for the last unit of a SKU (`on_hand - reserved == 1`), exactly one transaction commits; the second receives HTTP 409 Conflict. Invariant: `on_hand - reserved >= 0` is never violated. |
| **FR04** | Authoritative Server-Side Pricing and Tax | The system shall calculate item subtotals, regional shipping fees, and regional taxes on the server using active policy records. Any client-supplied pricing or tax values shall be disregarded. | Customer, Store Manager | **Must** | For all test orders, the persisted order total strictly matches `SUM(qty * unit_price) + shipping_fee + (subtotal * tax_rate)`. Altered client totals do not influence the stored record. |
| **FR05** | Idempotent Payment Confirmation | The system shall verify the HMAC-SHA256 signature of external payment callbacks and enforce uniqueness on `(gateway_id, event_id)`. | Payment Gateway, Finance Reviewer | **Must** | Submitting the same signed callback 10 times results in exactly 1 payment record inserted, exactly 1 order state update to `PAID`, exactly 1 shipment outbox entry, and 10 identical HTTP 200 responses. |
| **FR06** | Enforce Order Lifecycle State Machine | The system shall enforce guarded state transitions: `PLACED` -> `PAID` -> `PACKED` -> `DISPATCHED` -> `DELIVERED` -> `CLOSED`. Invalid jumps shall be rejected. | Warehouse Picker, Customer | **Must** | Direct transition from `PLACED` to `DISPATCHED` returns HTTP 400 Bad Request. Transition to `DISPATCHED` succeeds only if `state == 'PACKED'` and picking confirmation is recorded. |
| **FR07** | Pick-List Generation and Queue Isolation | The system shall expose pick lists containing only paid orders with active reservations assigned to the picker's warehouse region. | Warehouse Picker | **Should** | The picker endpoint returns only orders where `state == 'PAID'`, reservation status is active, and the order's regional assignment matches the picker's operational zone. |
| **FR08** | Reservation Expiry and Late Payment Reconciliation | The system shall release unpaid stock reservations after a 15-minute lease window. If a payment callback arrives after expiry, the system shall re-reserve stock if available; otherwise, it shall flag the order as `NEEDS_REFUND` and trigger the approval-controlled refund workflow. | Inventory Control, Warehouse Picker | **Must** | An expired reservation is released back to available pool (`reserved -= qty`). A late callback on an expired order without available inventory transitions order to `NEEDS_REFUND` and creates an automatic refund request. |
| **FR09** | Dispatch Execution and Tracking Milestones | The system shall record courier parcel tracking tokens upon physical dispatch and expose milestone updates (`DISPATCHED`, `DELIVERED`) to authorized customers. | Customer, Courier API | **Should** | Calling dispatch records a carrier tracking number and transitions order to `DISPATCHED`. The customer tracking endpoint returns only timestamps and milestones belonging to the authenticated customer. |
| **FR10** | Dual-Control Return and Refund Governance | The system shall maintain separate states for refund lifecycle: `REQUESTED` -> `APPROVED` / `REJECTED` -> `EXECUTING` -> `EXECUTED` (or `FAILED`). Human finance approval is mandatory for amounts > \$50.00. | Support Agent, Finance Reviewer | **Must** | Invoking `/refunds/{id}/execute` without prior `APPROVED` state returns HTTP 400. Attempted approval by non-finance roles returns HTTP 403. Failed execution retains `APPROVED` state for safe retry. |
| **FR11** | Transactional Outbox for External Synchronization | The system shall persist external dispatch and refund intents in a transactional outbox table within the same transaction as local state changes. A background worker shall retry failed external calls with exponential backoff. | Integration Worker, Courier API | **Must** | Simulating a network failure or worker crash does not lose integration intents. Worker retries use the stable `correlation_key` to prevent duplicate carrier booking or double refunds. |
| **FR12** | Immutable Audit Trail and Reporting Views | The system shall record an append-only audit entry for every state transition and administrative action, capturing actor ID, action type, entity ID, entity version, and UTC timestamp. | Administrator, Store Manager | **Should** | Every order transition and refund approval inserts an audit row. Regional reporting endpoints aggregate sales and refund totals accurately from underlying transaction logs. |
| **FR13** | Versioned Regional Policies (Expansion) | The system shall maintain independent, versioned policy records for 12 geographic operating regions (governing local sales tax, shipping fees, and refund approval thresholds). | Administrator, Store Manager | **Must (Exp)** | Each order snapshots the active policy version at creation. Updating a regional tax rate creates a new version; existing orders retain their historical snapshot total. |
| **FR14** | Edge Scanner Buffering and Safe Ingestion (Expansion) | The system shall accept buffered batches of warehouse barcode scans containing `node_id`, `event_id`, `observation_time`, and `schema_version`. Events shall be deduplicated on synchronization. | Warehouse Scanner, Inventory | **Must (Exp)** | Submitting a batch of 10 scan events with duplicate `(node_id, event_id)` pairs applies each unique inventory movement exactly once. Outdated observation timestamps are flagged as stale. |
